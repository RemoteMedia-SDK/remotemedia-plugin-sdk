# Linux CPU provider checkpoint

`remotemedia-workload-sandbox` exposes a host-side launch contract for build, install, and serve. The Linux CPU provider gives each run a standalone gVisor sandbox, a private cgroup v2 leaf, a read-only root filesystem and input mounts, and a bounded scratch tmpfs. The trusted host chooses the inputs and guest arguments after authorization and keeps its artifact and capacity leases until teardown is confirmed. Serving exposes a byte stream to the assigned guest-loopback port through a trusted relay in the root filesystem.

The provider reserves an empty private directory before the host stages a verified artifact. It mounts the staged source, wheel, and model trees from that reservation. Dropping an unstarted reservation removes its files. A started reservation stays in the recovery record until the runtime no longer lists the workload and the cgroup is gone. The real fixture confirmed that staged bytes remained after abrupt worker exit and that restart reconciliation removed the files and cgroup. The workload lifetime includes runtime startup.

Configure a worker with the pinned `runsc` binary and adjacent sidecars from the same verified release, a trusted immutable root filesystem containing the relay, and a private state directory. The provider verifies the executable digest and requires matching sidecar release metadata. Give the worker a dedicated cgroup v2 subtree with `cpu`, `memory`, and `pids` enabled for its children. The worker needs permission to set and read the child controls and kill a child cgroup during recovery. It holds exclusive locks on the state directory and the delegated subtree. The operator must keep both available across service restarts. [gVisor release](https://github.com/google/gvisor/releases/tag/release-20261116.0) · [gVisor installation](https://gvisor.dev/docs/user_guide/install/)

Build `remotemedia-workload-relay` for the guest image and set its guest path as the relay program. It connects only to the assigned IPv4 loopback address. The relay test passed on Linux with a 128 KiB binary upload, a partial response without a newline, input half-close, and rejection of a non-loopback address. The pinned gVisor fixture also passed with a statically linked build of the production relay in its guest root filesystem.

The provider writes and reads back the CPU, memory, zero-swap, and host-task caps before it invokes `runsc`. The foreground runtime owns the guest exit status. For serving, the provider waits for the running state and verifies cgroup membership before it exposes the relay. Startup reconciliation removes any leftover sandbox and validates cgroup teardown before clearing the bundle record. A cleanup failure leaves the record for recovery and returns `CleanupPending` to the host.

The provider sets `umask 022` in the runtime child so gVisor can create traversable guest mount points. The provider creates its host state and reservation roots with private permissions. The pinned gVisor fixture with the production relay passed while the worker used `umask 077`.

## Verified locally

The focused `runsc_cpu` integration test passed with gVisor `release-20261116.0` on Ubuntu 24.04.3 under WSL2, kernel `5.15.167.4-microsoft-standard-WSL2+`. The downloaded release archive matched the published SHA-512 checksum. The test ran a synthetic static program as a non-root user with zero effective capabilities and no new privileges. It checked read-only input, a 16 MiB scratch filesystem, loopback-only networking, and absence of host paths, host cgroup controls, the Docker socket, and NVIDIA devices. It read back the 500 milli-CPU, 128 MiB memory, zero-swap and 64 host-task limits from the active cgroup. It checked fast command exit, a private relay round trip, stream closure on stop, deadline and dropped-handle cleanup, and cleanup after the worker exited before teardown. The Windows package check compiled the portable provider contract.

Run the focused fixture from the Plugin SDK repository on Linux with an installed static C toolchain. Set `RM_SPACE_TEST_RUNSC` to the absolute path of the pinned runtime and `RM_SPACE_TEST_CGROUP` to an exclusively reserved test subtree with the controllers enabled. Set `RM_SPACE_TEST_RELAY` to a statically linked build of the release relay to exercise it in the guest. Use `cargo test --locked -p remotemedia-workload-sandbox --features test-runsc --test runsc_cpu`.

## Exclusive device ownership

`RunscProvider::open_for_exclusive_device` binds a canonical physical GPU UUID to the provider's state directory and delegated cgroup. Every provider on a host must use the same persistent local registry, owned by the provider account with mode `0700`. Keep it outside all guest and provider state mounts and protect its parent directories. The provider locks a stable per-device directory and atomically persists the binding before admitting work. The binding includes the Linux boot ID and both directories' device and inode identities. A restart must recover the original scope. After a host reboot the same configured paths may acquire fresh inodes before reconciliation.

The bound provider allows one outstanding workload bundle, including staging. The slot becomes available after the bundle is removed following confirmed cleanup. Loss of the process lock leaves the durable device binding in place. `release_exclusive_device` requires sole provider ownership and rechecks the pinned runtime before reconciling and verifying that its workload state is empty. It then releases the binding for a different provider. [Signed device admission](../../../../remotemedia-scaling/openspec/changes/isolate-space-workloads/implementation.md#named-cuda-admission)

The pinned WSL2 gVisor fixture used synthetic UUIDs and CPU workloads. It denied a second staged or active bundle and a competing provider for the same UUID. A different UUID remained usable. It denied a replacement state inode on the same boot. After the owner process exited with an active sandbox, only the original provider could recover and confirm teardown before another provider acquired the UUID. CUDA device exposure and physical acceptance remain open.

## Offline Python guest

Install the executable `guest/remotemedia-space-launch` and the Spaces `guest_bootstrap.py` and `static_space.py` under `/opt/remotemedia` in the trusted image. Provide trusted CPython at `/usr/bin/python3`, uv at `/usr/local/bin/uv`, and the production loopback relay. The launcher requires serving inventory version 2, verifies the ABI and the approved `major.minor` or `major.minor.patch` version, and checks the exact mounted wheel inventory before invoking uv. It creates the venv and installer scratch under `/work`, then runs uv with explicit environment and arguments, no indexes, and required hashes for direct local wheel paths. Roll out the SDK Base inventory producer and guest image together. Each run installs into its own fresh environment. [SDK Base inventory](../../../../remotemedia-sdk-base/openspec/changes/isolate-space-workloads/implementation.md) · [uv sync options](https://docs.astral.sh/uv/reference/cli/#uv-pip-sync)

The WSL2 fixture installed the exact CPython 3.12.3 lock with 49 wheels in two concurrent gVisor guests. Real Gradio 6.14.0 accepted uploads and streamed results through the production relay. Each guest wrote a marker into its own venv and saw fresh state on its first request. Stopping the first run left the sibling's marker and relay available. A wrong CPython patch with the same ABI was rejected before uv. Separate installer probes rejected a missing wheel, an incompatible wheel tag, and a wheel with changed bytes. The installation and dependency check completed with synthetic ambient uv configuration, index and interpreter settings. The install-phase provider fixture confirmed the network boundary. Eight launcher unit tests passed on Linux and Windows.

Scaling Runner calls the SDK Base bridge for opt-in Linux CPU launches. Deployment-host evidence and physical CUDA acceptance remain release gates. [Scaling verification](../../../../remotemedia-scaling/openspec/changes/isolate-space-workloads/implementation.md)

## Live CPU readiness

`RunscProvider::check_ready` reads the delegated controller set, checks the dedicated provider state and trusted guest launcher and relay, verifies the pinned runtime digest, and queries the runtime's container registry. The probe creates no reservation or workload. Runner uses the result for placement and rechecks it before staging a fresh protected run.

## Disposable source builds

`RunscProvider::build_python_wheel` verifies the worker-approved source distribution and build dependency wheels while staging them into read-only guest mounts. The build launcher reads version 1 of the ABI-bound inventory. It makes a fresh venv, syncs the pinned wheel closure with hashes, and uses offline uv to build the approved wheel from the archive through PEP 517. The gVisor build has private scratch and loopback, with the configured CPU, memory, process, scratch, and lifetime limits. [uv build options](https://docs.astral.sh/uv/reference/cli/#uv-build)

The host collects stdout into an anonymous bounded file. It releases that file only when the byte count and SHA-256 match the worker's approved output and gVisor confirms a successful exit and teardown. Input or output changes, build failure, and cancellation leave no wheel for the publisher. [Operator build command](../../../../remotemedia-scaling/openspec/changes/isolate-space-workloads/implementation.md)

The WSL2 gVisor fixture verified exact output, wrong digest, oversized output, failed exit, and timeout. The native Runner built a synthetic PEP 517 wheel with a pinned build dependency. It rejected altered source or dependency bytes and a mismatched Python ABI. SIGTERM and live policy revocation returned no wheel and removed the build bundles and workload cgroups. The guest launcher tests passed for the existing serving path.
