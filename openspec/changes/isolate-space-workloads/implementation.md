# Linux CPU provider checkpoint

`remotemedia-workload-sandbox` exposes a host-side launch contract for build, install, and serve. The Linux CPU provider gives each run a standalone gVisor sandbox, a private cgroup v2 leaf, a read-only root filesystem and input mounts, and a bounded scratch tmpfs. The trusted host chooses the inputs and guest arguments after authorization and keeps its artifact and capacity leases until teardown is confirmed. Serving exposes a byte stream to the assigned guest-loopback port through a trusted relay in the root filesystem.

Configure a worker with the pinned `runsc` binary and adjacent sidecars from the same verified release, a trusted immutable root filesystem containing the relay, and a private state directory. The provider verifies the executable digest and requires matching sidecar release metadata. Give the worker a dedicated cgroup v2 subtree with `cpu`, `memory`, and `pids` enabled for its children. The worker needs permission to set and read the child controls and kill a child cgroup during recovery. It holds exclusive locks on the state directory and the delegated subtree. The operator must keep both available across service restarts. [gVisor release](https://github.com/google/gvisor/releases/tag/release-20261116.0) · [gVisor installation](https://gvisor.dev/docs/user_guide/install/)

The provider writes and reads back the CPU, memory, zero-swap, and host-task caps before it invokes `runsc`. The foreground runtime owns the guest exit status. For serving, the provider waits for the running state and verifies cgroup membership before it exposes the relay. Startup reconciliation removes any leftover sandbox and validates cgroup teardown before clearing the bundle record. A cleanup failure leaves the record for recovery and returns `CleanupPending` to the host.

## Verified locally

The focused `runsc_cpu` integration test passed with gVisor `release-20261116.0` on Ubuntu 24.04.3 under WSL2, kernel `5.15.167.4-microsoft-standard-WSL2+`. The downloaded release archive matched the published SHA-512 checksum. The test ran a synthetic static program as a non-root user with zero effective capabilities and no new privileges. It checked read-only input, a 16 MiB scratch filesystem, loopback-only networking, and absence of host paths, host cgroup controls, the Docker socket, and NVIDIA devices. It read back the 500 milli-CPU, 128 MiB memory, zero-swap and 64 host-task limits from the active cgroup. It checked fast command exit, a private relay round trip, stream closure on stop, deadline and dropped-handle cleanup, and cleanup after the worker exited before teardown. The Windows package check compiled the portable provider contract.

Run the focused fixture from the Plugin SDK repository on Linux with an installed static C toolchain. Set `RM_SPACE_TEST_RUNSC` to the absolute path of the pinned runtime and `RM_SPACE_TEST_CGROUP` to an exclusively reserved test subtree with the controllers enabled. Use `cargo test --locked -p remotemedia-workload-sandbox --features test-runsc --test runsc_cpu`.

The SDK Base artifact lease handoff and Spaces gateway still need to call this provider. The fixture uses synthetic commands and a byte echo service. Wheel installation, a real Gradio upload and streamed response, deployment-host evidence, and physical CUDA acceptance remain release gates. The provider reports CUDA as unsupported.
